# AOSR

**一个从空镜像开始、自己长出来的 agent 操作系统。**

AOSR 启动时什么都没有。模型在一串任务上工作时，AOSR 会把学到的东西保存成可以运行的形式：

- **能力**：模型写下的函数，并且已验证的解法离开它就不成立。之后的每个任务都会加载这些能力，每次调用都会被追踪。
- **程序**：已经做对的完整解法。遇到新任务时，AOSR 先在任务示例上把它们跑一遍，把最接近的几个展示给模型；如果某个程序已经完全吻合，这道题不调用模型就直接解出。
- **它自己的内核**：操作手册和检索策略，由 AOSR 根据自己的失败来改写。只有当改写版在同一批近期任务上比原版解出更多时，才会被保留。

每一个状态都是带父指针、按内容寻址的镜像：可以启动、比较差异、敲掉其中的能力，也可以回放它是怎样长出来的。模型调用和沙箱运行都有缓存，因此一次生长可以离线精确重放。

## 结果

所有数字都来自一个小而便宜的模型（Claude Haiku 4.5，关闭扩展思考）在各个镜像上工作。对照组是同一个模型从空镜像出发，在任何生长过程都没有读过的 held-out 任务上，使用相同的模型调用次数。区间是按任务配对 bootstrap 得到的 95% 置信区间。

**ARC-AGI-1，400 道 evaluation 任务**，每题两次模型调用（写一个程序，再修复一次）：

| 镜像 | 解出 | 模型调用 | 美元（标价） |
|---|---|---|---|
| 空镜像（`head_0`） | 35 | 774 | 5.45 |
| 同一模型在 200 道训练任务上长出的镜像 | **45**（+2.5 个百分点，95% CI [+0.3, +4.8]） | 766 | 6.06 |
| 空镜像，每题四次调用 | 44 | 1490 | 10.65 |

长出的镜像与调用次数翻倍的空镜像持平，成本只有它的 57%。45 个解里有 4 个根本没有调用模型：在训练任务上长出的某个程序已经完全吻合。

**AppWorld，57 道 dev 任务**（9 个 app、457 个 API 组成的生态；任务由基准自带的状态检查判定），每题最多 20 轮：

| 镜像 | 8 轮内解出 | 12 轮内 | 20 轮内 | 模型调用 |
|---|---|---|---|---|
| 空镜像 | 11 | 15 | 21 | 646 |
| 在 90 道训练任务上长出的镜像 | **17**（+10.5，[0.0, +21.1]） | **22**（+12.3，[0.0, +24.6]） | 24（+5.3，[−5.3, +15.8]） | 407 |

长出的镜像 11 轮就能解出空镜像 20 轮解出的量，调用少 37%。它长出了 58 个能力，最深三层：账户与登录服务、通用分页器、各个 app 的数据读取，以及建立在这些之上的任务级操作。

**内核会改写自己。** 在一次 200 题的 ARC 生长中，每 50 题做一次演化，四次提议里有三次通过了 A/B 门控。

- 系统写给自己的操作手册，最初是"先描述规则、在每个示例上检查、手动走一遍代码"。之后又加入了针对它自己观察到的失败的规则，例如不要提交含有未定义 helper 的代码。
- 最后一步它还调整了检索策略：最多展示三个先前的程序，但只展示已经答对至少 80% 示例单元格的那些。这正是下面过度信任的失败所揭示的教训。
- 在 AppWorld 上，三次提议都没有通过。

但这些改写在 held-out 任务上没有带来可测出的提升：在 100 道 dev 任务上，演化后的镜像解出 34 题，只把它的手册放到空镜像上解出 31 题，而空镜像两次运行分别是 36 和 33。门控接受的是在最近 30 道 stream 任务上有帮助的修改，在这个窗口大小下，它分不清真实的改进和噪声（见下文）。

### 没有奏效的部分

以下都按实测报告。

- **无差别展示库会适得其反。** 在 100 道 dev 任务上，一个在索引里列出三个无关 helper 的镜像解出 26 题，空镜像解出 36 题。模型调用了一个名字听起来对、结果却不对的 helper。隐藏索引后，它解出 32 题。
- **在 AppWorld 上，模型过度信任长出的 helper。** 第一次运行时，提示词说 helper 可以"直接调用"，结果模型一到四轮就交出错误答案，成功数是 20 对 24。改成"每个 helper 对它所来自的任务是对的，但未必适合这一题"，并且展示复用次数之后，结果反转了。
- **ARC 上起作用的不是 helper，而是先例程序。** 在早期一次 80 道训练任务的试点里，镜像由同一模型在开启扩展思考时长出：只给 helper 是 22 对 23；加上最接近的先前程序后是 28。
- **内核的 A/B 门控有噪声。** 同一个镜像跑两次，在 100 道题上相差约 3 个百分点。所以在默认 margin 为 3 时，30 题的窗口大约每十次会接受一次实际无效的修改。

## 快速开始

```bash
pip install git+https://github.com/Meirtz/Limen
aosr fetch                                   # 固定版本的 ARC-AGI-1，下载到 ~/.cache/aosr
aosr boot                                    # head_0：空镜像
export AOSR_ALLOW_LIVE=1                     # 模型调用通过 `claude` CLI
aosr grow --run demo --n 50 --checkpoints 25,50 --out runs/demo --epoch-every 25
aosr eval --image demo/n50 --arm grown --split dev --out runs/demo/grown.jsonl
aosr eval --image head_0 --arm empty --split dev --out runs/demo/empty.jsonl
aosr report --budget 2 runs/demo/empty.jsonl runs/demo/grown.jsonl \
    --compare runs/demo/empty.jsonl@2,runs/demo/grown.jsonl@2
aosr show demo/n50                            # 看看它长出了什么
aosr demo --run demo --grow-log runs/demo/grow.jsonl --out demo.html runs/demo/*.jsonl
```

真实调用需要 PATH 上有 [`claude` CLI](https://docs.anthropic.com/en/docs/claude-code)。不设置 `AOSR_ALLOW_LIVE=1` 时，所有模型调用都会被拒绝，只能从缓存回放。AppWorld 需要 Python 3.11 和 `pip install appworld`（`aosr grow --world appworld ...`）。

`aosr demo` 生成的两个页面展示了长出来的镜像是什么样子（下载后用浏览器打开）：[docs/demo/arc-grown.html](docs/demo/arc-grown.html)（evaluation 划分结果背后的镜像）和 [docs/demo/arc-grown-and-evolved.html](docs/demo/arc-grown-and-evolved.html)（同时改写了内核的一次运行）。

## 工作原理

**镜像。** store 保存按内容 SHA-256 寻址的不可变对象：能力、程序和内核槽位（`notes`、`policy`）。一个镜像指定每样东西的一个版本，加上使用计数，并指向它的父镜像。`aosr lineage`、`aosr show`、`aosr knockout`、`aosr slot` 都作用于镜像。

**解一道题。**

- 内核把镜像中的能力逐个加载进沙箱子进程，一个能力坏了不会拖垮其他能力。
- 把每个单参数能力和每个已存程序在任务示例输入上跑一遍，按与示例输出的接近程度排序。
- 若有完全吻合的，验证后直接提交，不调用模型。
- 否则把最接近的能力和程序展示给 worker，交替进行全新尝试和修复；修复时会告诉它输出错在哪里。

**生长。**

- 一个在其任务 held-out 测试上正确的解，会把整个程序作为先例贡献出来。
- 它还会贡献每个必需的 helper：用恒等存根替换后解就会失败的那种。helper 会连同它调用的函数一起准入。
- 以下 helper 不准入：读取模块级状态的；与现有能力行为完全相同的（它的调用方会被改为指向那个能力）。
- 去掉 helper 后的 `solve` 必须在扩展后的库上仍然通过验证。
- 在 AppWorld 上，先由一次整理调用把成功的 episode 改写成 helper 加上 `solve(apis)`，再在该任务世界的全新副本中重放，通过后才保留任何东西。

**演化内核。**

- 每隔 N 道任务，一个工程师模型读取近期失败与成功的摘要，提出新的操作手册，也可以提出新的策略（worker 能看到多少库和先前程序）。
- 提案在最近的 stream 任务上与当前内核对比：使用新的采样，并且镜像里不包含这些任务自己贡献的东西。
- 只有多解出至少 `margin` 道时才保留。

**测量。** 尝试按固定顺序进行，所以一次预算为 B 的运行可以同时给出所有 b ≤ B 的结果。各组在相同调用次数下用配对 bootstrap 比较。不设置 `AOSR_UNLOCK_EVAL=1` 就无法加载 ARC 的 evaluation 划分。在 macOS 上，沙箱读不到任务数据，也无法联网。CI 全程离线，任何试图启动 `claude` CLI 的测试都会失败。

## 目录

```
src/aosr/   操作系统本体：store、内核、沙箱、准入、生长、演化、评测、统计、
            世界（ARC-AGI-1、AppWorld）、CLI、演示页面
src/limen/  Limen：本项目由之而来的实验检查器
```

Limen 检查一次实验是否按它声称的方式运行：处理是否真正执行、两组之间是否没有其他差异、门控是否可能失败、held-out 数据是否没有泄漏。见 [docs/limen-checker.zh.md](docs/limen-checker.zh.md)。
